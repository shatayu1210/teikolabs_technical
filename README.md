# Teiko Technical Challenge

Analysis of immune cell population data from a clinical trial for the drug candidate miraclib. Built for the Teiko software engineer take home challenge.

## Running this

You need Python 3.11 and `make`. From the repo root:

```
make setup       # installs dependencies
make pipeline    # builds the database, loads the data, runs parts 2 to 4
make dashboard   # starts the dashboard at localhost:8501
make test        # runs the test suite
make clean       # deletes the database and generated output, if you want a fresh run
```

`make test` and `make clean` aren't required by the challenge, they're just convenient while working on this. The three the grader actually needs are setup, pipeline and dashboard.

If you're opening this in GitHub Codespaces, the dev container installs everything automatically when the container starts, so `make pipeline` and `make dashboard` should just work.

## What's in here

```
load_data.py        Part 1, builds the database and loads cell-count.csv
db/schema.sql        the table definitions
src/
  db.py               connection and schema helper, shared by every script
  frequencies.py      Part 2, relative frequency per sample
  stats_analysis.py   Part 3, responder vs non-responder comparison
  subset_analysis.py  Part 4, baseline subset breakdown
dashboard/app.py     the Streamlit dashboard
tests/
  unit/               one file per analysis module, small fixtures with known answers
  integration/        runs the full pipeline against a tiny csv and checks it end to end
output/               tables and plots generated by make pipeline
```

Each analysis part is its own module with a small, focused job, and each one has a matching test file. That split exists so a change to, say, the stats logic can't quietly break the frequency calculation, and so each part can be tested and understood on its own without having to read the whole pipeline at once.

A few other structure choices worth explaining. `db.py` holds the connection and schema setup in one place, so `load_data.py`, the three analysis modules and the dashboard all talk to the database the exact same way instead of each rolling their own. The dashboard doesn't have any of its own calculation logic either, it just imports and displays the same functions the pipeline uses, so the numbers you see on screen and the numbers in `output/` can never quietly drift apart. Tests are split into `unit` (fast, one file per module, small hand built fixtures) and `integration` (slower, runs the real pipeline end to end), so you can run just the unit tests while iterating and the full set before pushing.

## What's in output

Running `make pipeline` fills this folder in:

- `frequencies.csv`, the full Part 2 table, one row per sample per population
- `stats_results.csv`, the Part 3 test results, one row per population with the p-value, adjusted p-value and whether it's significant
- `boxplots.png`, the Part 3 boxplots, responders vs non-responders
- `subset_summary.csv`, the Part 4 baseline breakdown by project, response and sex
- `part4_answer.txt`, the specific B cell average question from Part 4

These are committed as an example of what a real run produces, since the task asks for output files to be included, but they'll be overwritten the moment you run the pipeline yourself.

## Database schema

Three tables:

**subjects**: one row per patient (subject_id, project, condition, age, sex, treatment, response).

**samples**: one row per biological sample (sample_id, subject_id, sample_type, time_from_treatment_start).

**cell_counts**: one row per population per sample (sample_id, population, count), rather than one column per population.

I split it this way because, in the data, a subject's condition, age, sex, treatment and response never change across their samples, so repeating that on every row would just be duplicated data with no benefit. The `cell_counts` table being long format instead of five wide columns is the more important choice. It means Part 2's summary table is basically just this table joined and grouped, no reshaping needed. It also means the schema doesn't need to change if the panel grows, a sixth population later, or a different assay entirely, is just more rows.

That's also the answer to how this scales. With hundreds of projects and thousands of samples, this is still the same three tables, just more rows in each, and the indexes on `subject_id` and `sample_id` keep the joins fast as the row counts grow. If Bob later wants a new kind of analysis, say per-project trends over time, that's a new query against the existing tables, not a new table or a migration. The one thing I'd add before this got to real production scale is a proper `population` reference table (name, description, panel version), so cell types are validated on the way in rather than trusted as free text.

## Part 3: why these particular stats

**Mann-Whitney U test instead of a t-test.** Relative frequency data from a clinical cohort isn't guaranteed to be normally distributed, and a t-test assumes it is. Mann-Whitney compares the ranks of the two groups rather than their means, so it doesn't carry that assumption and it's much less thrown off by one or two outlier patients. For a dataset this size, that's the safer default.

**Benjamini-Hochberg correction.** Part 3 runs five separate tests, one per cell population, against the same two groups. Every time you run another test, the odds of one of them looking significant purely by chance go up. Benjamini-Hochberg adjusts the p-values to account for that, so a population only gets called significant if it holds up once you account for testing five things at once, not just because it happened to clear 0.05 on its own. Given the ask is to convince a skeptical colleague, this felt like the right bar to hold the result to.

## Testing

Unit tests build a tiny database with counts I picked by hand, so the expected answer is known ahead of time rather than just "does it run". The integration test runs `load_data.py` and all three analysis parts against a small csv, start to finish, to check the pieces actually work together. Run everything with `make test`.

## A couple of notes

Part 4's B cell average question is deliberately not restricted to PBMC or miraclib, it asks about melanoma males across every sample and treatment type, so that's how it's queried.

While testing Part 3, I ran into a good example of why percentages need care with this kind of data: if one population's count changes but the others don't, every population's *relative* frequency shifts anyway, because they all share the same total. The stats here are working on relative frequency on purpose, since that's what Part 2 and the question both ask for, but it's worth keeping in mind when reading the results, a shift in one population can nudge the others even if their raw counts never moved.
